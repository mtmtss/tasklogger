# 1. 目的と背景

## 1.1 解決したい課題

ユーザープロファイル(user_profile.md)の分析から、TaskLogger 利用者の最大のボトルネックは
**「大量のタスク候補を、今日の実行可能な量に圧縮する作業」**である(§3.3)。

- 研究・実装・発表準備・事務・生活タスクが並行し、候補が常に多い
- 締切・重要度・所要時間・気力・文脈を毎朝自分で秤にかけるのは認知負荷が高い
- 重いタスクをそのまま今日に置くと着手できず、「最初の一手」への分解が必要
- 「今日やらない」と決めることにも心理的コストがある(安心して退避させたい)

## 1.2 TaskLogger だからできること

一般のタスク管理アプリの AI 機能と違い、TaskLogger には**実際の作業記録**がある:

| TaskLogger 固有のデータ | 作戦生成での使い道 |
| --- | --- |
| タスクごとの実績時間(work_logs) | 「このタスクは過去に平均 50 分/回かかっている」という現実的な見積もり |
| null タスク(未割当の PC 時間) | 「タスク化されていない作業が 1 日 2 時間ある」ことを踏まえた計画量の調整 |
| 中断ログと end_reason | 中断されがちなタスク・時間帯の把握 |
| 日別の作業ペース | 「あなたの平常ペースは 1 日実働 4 時間」という現実的な上限設定 |

**実績に基づく計画**が本拡張のコアバリューであり、根性論的な TODO 圧縮との差別化点である。

## 1.3 確定した設計判断

| 論点 | 決定 |
| --- | --- |
| 実装形態 | **既存 TaskLogger アプリに組込み**(別アプリにしない)。作業ログ・タスクキャッシュ・設定・トレイ常駐をそのまま活用 |
| MVP スコープ | **今日の作戦生成のみ**。Inbox+AI 整理 / 日次レビュー / 研究アイデア DB は将来拡張(§10) |
| タスク基盤 | **Google Tasks に統一**(TickTick 連携はしない。TickTick からは移行) |
| 音声入力 | **Windows 標準音声入力(Win+H)を活用**。アプリ内のテキスト欄に OS 機能で喋って入力する。専用音声パイプラインは将来拡張 |
| LLM | **Gemini API**(Google)。既定モデル `gemini-2.5-flash`(無料枠運用可) |

# 2. アーキテクチャ

## 2.1 構成

```text
┌────────────────────────── TaskLogger (既存) ──────────────────────────┐
│  React UI ── invoke ──> Rust コマンド ──> SQLite (tasks / work_logs)    │
│                              │                    ▲                    │
│  [新] 今日の作戦カード         │                    │ 読取専用            │
│      └ generate_daily_plan ──┴──> [新] ai モジュール                    │
│                                     ├ context_builder (SQLite→文脈生成) │
│                                     ├ gemini_api (generateContent 呼出)    │
│                                     └ daily_plans (結果保存)            │
└──────────────────────────────────┬────────────────────────────────────┘
                                   │ HTTPS (生成時のみ)
                            Google Gemini API
```

- **ローカルファースト原則は不変**: タスク操作・記録・集計は従来どおりローカル完結。
  AI は「作戦の提案」という付加機能であり、失敗してもアプリの他機能に影響しない
- AI 呼び出しは Tauri の async コマンド + spawn_blocking で実行し、UI を一切ブロックしない
- 提案からの操作(今すぐやる / 今日やる)は**既存のローカルファーストコマンドを流用**する

## 2.2 新規モジュール(Rust)

```text
src-tauri/src/ai/
├── mod.rs              # コマンド定義 (generate_daily_plan, set_ai_api_key など)
├── gemini_api.rs       # Gemini API クライアント (reqwest blocking, responseSchema で JSON 保証)
├── context_builder.rs  # SQLite から入力コンテキストを収集・整形
└── plan_store.rs       # daily_plans テーブルの保存・取得
```

# 3. 機能仕様: 今日の作戦生成

## 3.1 トリガー

| トリガー | 動作 |
| --- | --- |
| 今日ページの「作戦を立てる」ボタン | その場で生成(10〜60 秒。生成中はカードにスピナー) |
| 再生成ボタン | 状態メモを編集して何度でも再生成(履歴は上書きでなく追記) |
| (設定でオン)その日最初のアプリ起動時 | 自動生成し、完了を OS 通知。既定はオフ |

## 3.2 入力コンテキスト(context_builder が組み立てる)

すべてローカル SQLite から収集。プロンプトは以下で構成する:

**(a) 固定プロファイル**(settings `ai_user_context`、ユーザーが設定ページで編集)
- 職業・研究テーマ・作業の癖・優先方針などの自由記述。user_profile.md の要約を貼ることを想定
- プロンプトの安定プレフィックスとしてキャッシュ対象(prompt caching)

**(b) タスク状況**
- 今日期限の未完了タスク全件(リスト名・タイトル・メモ・今日の実績時間・状態)
- 候補タスク(期限が近い順 + 停滞順で上位 30 件。期限・タイトル・メモ)
- 停滞タスク: 14 日以上作業ログがなく期限が過ぎている/近いもの(明示フラグ付き)

**(c) 実績データ(TaskLogger の強み)**
- 過去 7 日の日別実働時間(null タスク時間は「未割当」として区別して併記)
- 昨日の完了・中断タスクと所要時間
- 今日の作戦対象タスクそれぞれの過去実績(平均セッション時間・累計・直近作業日)
- 過去 30 日の平日/休日別の平均実働時間(計画量の上限の根拠)

**(d) 当日の状態**(任意入力、Win+H で音声入力可)
- 例:「午後から外出」「今日は気力が低い」「締切前なので研究優先」
- テキストボックス 1 つ。空でもよい

**(e) 現在日時・曜日**

## 3.3 出力(structured outputs で JSON 固定)

```json
{
  "must_do": [
    {
      "taskListId": "…",       // 既存タスクに対応する場合。null なら提案のみ
      "taskId": "…",
      "title": "発表スライドの構成を作る",
      "firstStep": "アウトラインを 3 項目だけ書く",
      "estimatedMinutes": 45,   // 過去実績があれば実績ベース
      "reason": "金曜締切。過去のスライド作成は平均90分/回なので今日は構成まで"
    }
  ],
  "if_possible": [ /* 同上、0〜3 件 */ ],
  "five_minute": [ /* 同上、0〜3 件 */ ],
  "not_today": [
    { "taskId": "…", "title": "…", "reason": "締切まで余裕があり、今日は発表準備を優先" }
  ],
  "advice": "直近7日の実働は平均3.5時間/日。今日は外出があるので必ずやるは2件に絞りました。"
}
```

- `must_do` は 1〜3 件。**重いタスクはタスクそのものではなく「最初の一手」を提示**する
- `estimatedMinutes` は過去実績を優先し、なければ AI の推定
- `not_today` は「安心して退避する」ためのセクション。理由を必ず付ける
- 出力スキーマは Gemini の `responseSchema` で強制し、パース失敗をなくす

## 3.4 UI(今日ページ)

- 今日ページ最上部に折りたたみ可能な**「今日の作戦」カード**を追加
  - 未生成時: 状態メモ入力欄 + 「作戦を立てる」ボタン
  - 生成後: セクション別リスト(必ずやる / できれば / 5分 / 今日やらない)+ advice
- 各提案項目のアクション(既存コマンド流用):
  - **[今すぐやる]** → 既存 `do_it_now`(候補タスクの場合)/ `start_task`(今日タスクの場合)
  - **[今日やるに入れる]** → 新コマンド `schedule_for_today`(due=today 化のみ。開始しない)
  - `taskId` が null の提案(分解された「最初の一手」など)はテキスト表示のみ(タスク化は将来拡張)
- 生成済みプランはその日の間は保持・表示(再起動しても daily_plans から復元)
- AI 未設定(API キーなし)の場合、カード自体を表示しない(既存 UI に影響ゼロ)

## 3.5 新規 Tauri コマンド

| コマンド | 内容 |
| --- | --- |
| `generate_daily_plan(note: string)` | コンテキスト収集 → Gemini API → 検証済み JSON を保存して返す(async) |
| `get_daily_plan()` | 今日の最新プランを daily_plans から取得(ローカル、即時) |
| `schedule_for_today(task)` | due=today 化のみ(`set_task_due_today_locally` + sync enqueue の流用) |
| `set_ai_api_key(key)` / `clear_ai_api_key()` | keyring への保存・削除 |
| `get_ai_status()` | { configured, model } (キーの有無のみ。キー本体は返さない) |

# 4. Gemini API 連携仕様

LLM は **Gemini API**(Google Generative Language API)を用いる。
選定理由: (1) Google AI Studio のキーで**無料枠運用が可能**(コスト面の決定要因)、
(2) Google アカウント・GCP は Tasks 連携で導入済み、(3) GAS 版でも Gemini を利用していた連続性。

## 4.1 モデルとパラメータ

| 項目 | 値 |
| --- | --- |
| 既定モデル | `gemini-2.5-flash`(設定 `ai_model` で変更可。選択肢: 2.5-flash / 2.5-flash-lite / 2.5-pro) |
| エンドポイント | `POST /v1beta/models/{model}:generateContent`(キーは `x-goog-api-key` ヘッダ) |
| 出力形式 | `generationConfig.responseMimeType: "application/json"` + `responseSchema`(§3.3 のスキーマ。Gemini の OpenAPI 風形式) |
| maxOutputTokens | 8192(thinking 分の余裕込み) |
| thinking | 既定(dynamic)。明示設定しない |
| タイムアウト | 180 秒 |
| リトライ | 429 / 5xx は 1 回リトライ(SDK なし・reqwest 直叩きのため自前) |

## 4.2 プロンプト構成

```text
systemInstruction:
  [固定] 役割定義(実績に基づく現実的な計画を立てるコーチ。過剰計画を戒める方針)
  [固定] 出力ルール(最初の一手への分解、実績ベース見積もり、退避理由の必須化)
  [準固定] ユーザープロファイル (ai_user_context)
contents (user):
  [可変] タスク状況 + 実績データ + 当日の状態 + 現在日時
```

- Gemini 2.5 系は implicit caching が自動適用されるため、明示のキャッシュ制御は行わない
- 可変データは必ず user 側に置き、systemInstruction は日をまたいでも安定に保つ

## 4.3 API キー管理

- キーは [Google AI Studio](https://aistudio.google.com/) で発行(無料、クレジットカード不要)
- **Windows 資格情報マネージャー(keyring)** に保存(service "TaskLogger", user "gemini_api_key")。SQLite・設定ファイルには置かない(既存の refresh token と同じ方針)
- 設定ページに入力欄(パスワード型)。保存時に models API `GET /v1beta/models/{model}` で疎通確認
- キー未設定時は AI 機能全体が無効(明示的オプトイン)

## 4.4 コスト目安(仕様書に明記してユーザーが判断できるように)

1 回の生成 ≒ 入力 3〜5K トークン + 出力 1K トークン:

| モデル | 無料枠 | 有料時の目安 (1回 / 毎日2回×30日) |
| --- | --- | --- |
| gemini-2.5-flash (既定) | **あり**(1日あたりのリクエスト上限内なら $0) | 約 $0.005 / 約 $0.3/月 |
| gemini-2.5-flash-lite | あり | 約 $0.002 / 約 $0.1/月 |
| gemini-2.5-pro | 限定的 | 約 $0.02 / 約 $1/月 |

1 日数回の作戦生成なら **flash の無料枠に収まる想定**(上限超過時は 429 → 時間を置いて再試行)。

## 4.5 エラー処理

| 状況 | 挙動 |
| --- | --- |
| ネットワーク不通 / タイムアウト | カードにエラー表示 + 再試行ボタン。他機能に影響なし |
| 400/401/403(キー無効) | 「API キーを確認してください」+ 設定ページへの導線 |
| 429(無料枠上限含む) | 1 回リトライ後、時間を置くよう案内 |
| 5xx | 1 回リトライ後、時間を置くよう案内 |
| `promptFeedback.blockReason` / `finishReason != STOP` / スキーマ外応答 | 汎用エラー表示(内容起因のためユーザーに再生成を促す) |

# 5. データモデル追加

## 5.1 daily_plans テーブル(マイグレーション v2)

```sql
CREATE TABLE daily_plans (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  plan_date    TEXT NOT NULL,          -- JST yyyy-MM-dd
  generated_at TEXT NOT NULL,          -- ISO 8601
  input_note   TEXT NOT NULL DEFAULT '', -- 当日の状態メモ
  model        TEXT NOT NULL,
  plan_json    TEXT NOT NULL           -- §3.3 の JSON
);
CREATE INDEX idx_daily_plans_date ON daily_plans(plan_date);
```

- 追記型(再生成は新規行)。過去プランは将来の日次レビュー・文脈材料に使う
- Sheets 同期の対象外(ローカルのみ)

## 5.2 設定キー追加

| キー | 内容 |
| --- | --- |
| `ai_model` | 既定 `gemini-2.5-flash` |
| `ai_user_context` | 固定プロファイル自由記述 |
| `ai_auto_plan` | "true" でその日初回起動時に自動生成(既定 false) |

# 6. プライバシーとセキュリティ

- 生成時に **タスクのタイトル・メモ・作業実績の要約が Google の Gemini API に送信される**。
  設定ページの AI セクションにこの旨を明記し、キー設定 = 同意とする(明示的オプトイン)
- **無料枠(AI Studio キー)では入力がサービス改善に利用され得る**(Google の規約による)。研究上の機微情報を扱う場合は課金を有効にしたキー(有料枠はサービス改善への利用なし)の使用を推奨。この注意を設定 UI と README に明記
- API キーは keyring のみ。ログ・エラーメッセージにキーを含めない
- 送信するのは §3.2 のコンテキストのみ。work_logs の生データ全件は送らない(集計値と直近分のみ)

---

# 7. 非機能要件

- **UI 非ブロック**: 生成中も全タスク操作が通常どおり動く(既存の 100ms 原則は AI 以外に適用)
- **フェイルセーフ**: AI モジュールの失敗がタスク記録・同期に波及しない(モジュール分離)
- **オフライン**: AI 機能のみ停止、その他は全機能動作
- macOS 対応: AI モジュールは OS 非依存(keyring は既に apple-native feature 対応済み)

# 9. 検証方法

- E1: 接続テスト(実キー)+ 不正キーで 401 ハンドリング確認
- E2: サンプルデータ + 実ログで context_builder の出力を目視確認(トークン数が想定内か)
- E3: 1 週間の実運用で「提案の妥当性」「見積もりと実績の乖離」を確認(daily_plans に履歴が残るので突合可能)
- 全体: AI 無効(キー未設定)状態で既存機能のリグレッションがないこと

# 11. まとめ

本拡張は「タスクを増やす AI」ではなく、**実績データに基づいて今日を現実的なサイズに圧縮する AI** である。

```text
TaskLogger が記録してきた実績(実働時間・null 時間・中断パターン)
        ↓
Gemini API が締切・停滞・当日の状態と合わせて判断
        ↓
必ずやる 1〜3 件(最初の一手つき)+ 安心して退避できる「今日やらない」
        ↓
ワンクリックで「今すぐやる」(既存のローカルファースト操作へ接続)
```

MVP で計画→実行→記録のループを閉じ、第2弾の日次レビューで記録→振り返り→翌日の計画まで接続する。

# 12. 日次レビュー(第2弾・実装済み)

「今朝の作戦(daily_plans)」と「実際にやったこと(work_logs)」を突合し、責めずに次につなげる振り返りを生成する。今日の作戦と同じ Gemini 基盤を流用する。

## 12.1 入力コンテキスト(`review_builder`)

- 今朝立てた作戦(その日の daily_plans があれば、必ずやる/できれば/5分の各項目と見積もり)
- その日の全 work_logs: 完了/中断、所要時間、end_reason(無操作・スリープ由来を明示)、メモ
- 集計: タスク作業合計 / null(未割当)合計、完了件数 / 中断件数(うち自動中断)

## 12.2 出力(`responseSchema` で固定)

```json
{
  "done": ["論文の実験セクションを30分進め図3を差し替えた"],
  "incomplete": [{ "title": "申請書の確認", "reason": "発表準備を優先したため未着手" }],
  "tomorrow": [{ "taskListId": "…", "taskId": "…", "title": "申請書の不足情報を確認", "reason": "締切が近い" }],
  "research_progress": "実験セクションが図まで揃い、考察の骨子が見えた",
  "summary": "計画の必ずやる2件は達成。無操作中断が3件あり午後は集中が切れ気味。明日は申請書を最初の一手に。"
}
```

- **計画と実績の乖離**があれば summary で一言触れる
- 自動中断(idle/sleep)が多い場合は集中の妨げ・離席として扱い、本人を責めない
- `tomorrow` の各項目が既存タスクに対応すれば taskListId/taskId を返し、UI から「今日やるに入れる」で `schedule_for_today` に接続

## 12.3 データ・コマンド・UI

- テーブル: `daily_reviews`(マイグレーション v3、追記型)。当日の最新を復元
- コマンド: `generate_daily_review`(async)/ `get_daily_review`
- UI: 今日ページ末尾の「今日の振り返り」カード(既定は折りたたみ。1日の終わりに開く想定)。できたこと/未完了と理由/明日候補/研究の前進/総括を表示

## 12.4 ループの完成

```text
                    ↑                                                    │
                    └──────────  明日候補を「今日やる」で翌日へ  ←────────┘
```
